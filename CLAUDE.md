# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Home Plan is a browser-based floor plan editor: draw straight and curved walls in a 2D canvas editor, place doors and windows from a left-hand palette, and see a live Three.js 3D view. It is plain ES modules with no build step, no package.json and no npm dependencies. Three.js (0.169.0) is loaded from cdn.jsdelivr.net via the import map in `index.html`.

Since the backend landed there is also a small Node server (`server/`) in the **same** container: it serves the editor and a JSON API so invited users can keep plans on the server and share read-only links. It uses `node:sqlite`, `node:crypto` and `node:http` only — still no npm dependencies — and needs **Node >= 22.5**. The editor itself stays local-first: without an account everything works exactly as before, in `localStorage`.

## Commands

- **Run the editor alone:** any static server works for front-end-only work, e.g. `python3 -m http.server 8000` — the API calls fail quietly and the account bar just offers "Sign in".
- **Run everything:** `node server/server.js` (Node >= 22.5), or the container below. `PORT`, `DATA_DIR`, `BASE_URL`, `SESSION_DAYS`, `INVITE_HOURS` and `SECURE_COOKIES=1` are the knobs.
- **Run tests (node):** `node run-tests.mjs` — model tests always, server tests when the runtime has `node:sqlite`, skipped with a message otherwise. Both suites on any machine with Docker:
  `docker run --rm -v "$PWD":/app -w /app node:24-alpine node run-tests.mjs`.
- **Run tests (browser):** open `tests.html` — the model suite only.
- **Single test:** there's no filter flag. Tests are registered with `test(name, fn)` in `js/model.test.js` and `server/server.test.mjs`; temporarily filter the `tests` array or comment out others.
- **Docker:** `docker build -t homeplan . && docker run -d -p 8080:8080 -e BASE_URL=https://your.host -v homeplan-data:/data homeplan`. One image, one process; the database lives in the `/data` volume.
- **Add a user:** `docker exec -it homeplan add_user.sh someone@example.com` prints an invite link to send them; `--reset` re-issues one (and signs them out), `--list` shows who exists. There is no sign-up page and no email is sent.

## Architecture

- **`js/model.js`** is the single source of truth and has **no DOM access** — it must stay runnable under node, since tests import it directly. Same rule for `geometry.js`, `catalog.js` and `model.test.js`.
  - Graph structure: `nodes {id,x,y,level}`, `walls {id,a,b,thickness,height,level,bulge?,style?}` referencing node ids, `openings {id,wallId,type,t,width,swing?}` where `t` is the opening's centre offset in cm from wall node `a`. Walls sharing a node are joined.
  - **Curved walls:** `bulge` is the sagitta in cm — how far the middle of the arc sits off the middle of the chord, along `perp(unit(b - a))`. Absent or 0 means straight, and `toJSON` only writes it when it is set, so old plans round-trip unchanged. The arc kernel lives in `geometry.js` (`arcFromChord`, `arcPointAt`, `arcProject`, `arcSamples`, `arcOffset`, `bulgeFromSweep`, plus `sagittaThrough` / `splineBulges` for fitting a Catmull-Rom spline), and `wallArc/wallLength/pointOnWall/wallDirAt/projectOnWall/wallSamples` route every query through it. `t` is arc length, so openings, `freeGaps`, `fitOpening` and `splitWall` (which divides the sweep between the halves) need no special cases. Mitred joins use the **end tangents**, which leaves a hairline discontinuity where an arc meets a straight wall — accepted.
  - **Barriers:** `style` (see `catalog.WALL_STYLES`) is absent for a plain wall and set for the three barrier styles — `barrier_full`, `barrier_glass`, `barrier_railing` — which are ordinary walls carrying a lower height (100 cm by default). `wallStyleDefaults(level, style)` gives the thickness and height a style brings; `addWall({style})` and `updateWall({style})` apply it unless the call passes explicit values, and `_split` copies the style. Because `updateLevel` only carries walls whose height *equalled* the old level height, barriers keep their own height when a level grows. Openings are allowed on a barrier: `openingDims` clamps them to its height, so a door in a railing is simply a gap.
  - **Levels:** `levels [{id,name,height}]` ordered bottom to top. Elevations are computed, never stored (`levelElevation(id)` = sum of the heights below). Nodes, walls, floors and stairs carry a `level`; openings take theirs from their wall. Nodes belong to one level, so walls never join across levels. Geometry queries (`nodeNear`, `nearestWall`, `getOrCreateNode`, `addNode`/`addWall`, `mergeNodeIfNear`) default to `model.activeLevel` or take an explicit level; `bounds(level?)` and `computeWallPolygons(model, level?)` cover every level when the level is omitted.
  - `activeLevel` is UI state: it is **not** in `toJSON()`, so undo snapshots never record level switches. `load()` keeps it if that level still exists, otherwise falls back to the first level. `setActiveLevel(id)` emits a change.
  - **Floors** `{id,level,kind,points:[{x,y}],thickness}` are hand-drawn polygons; a `kind: 'slab'` spans `elevation - thickness … elevation`, while a `kind: 'cutout'` is never built and instead punches a hole in the slabs of its own level (`floorsCutBy` lists them). Missing `kind` loads as `'slab'`. **Stairs** `{id,level,x,y,width,length,angle,kind?,sweep?}` come in three kinds (`catalog.STAIR_KINDS`): a solid `straight` flight and an `open` one (floating treads) start at `(x, y)` — the start of the centre line — and climb `length` cm in direction `angle`, while a `spiral` turns `sweep` degrees about `(x, y)`, which is its **centre**, with `width` as the outer diameter. `angle` is any angle (normalised to 0…359, no quarter-turn snapping; the editor snaps to 15° while dragging the rotate handle). `stairsFootprint()` is 4 corners for a straight or open flight and a 16-gon for a spiral, so stairwells, hit-testing and bounds need no special case; `stairsInfo()` gives rise, step count (`round(rise / 18)`) and `treadAngle` for a spiral.
  - **Furniture** `{id,level,type,x,y,angle,width,depth,height,elevation}` is schematic: `(x, y)` is the footprint centre, `angle` is free, and the shape comes from `catalog.FURNITURE_TYPES` — each type is a few boxes written as fractions of the bounding box, so a resized piece keeps its proportions. Local axes are +x right and **+y front**, so the back (y = −0.5) is the face the editor snaps against a wall. `furnitureParts(type, size)` resolves them to cm and both renderers build from that one source. `floorHoles(floor)` returns the footprints of stairs on the level directly below **and** the outlines of cutouts on the same level that lie inside the floor — the 2D and 3D views cut these out. Containment has to be total (`polygonInFloor`), because `THREE.Shape.holes` has no meaning for a partial overlap.
  - `roomPolygonAt(point, level?)` traces the room under a point: it walks every face of the wall graph (dead ends pruned first), keeps the smallest face containing the point, and returns its inner wall faces, sampling the offset arc of any curved wall. That is what the **Floor fill** tool draws in one click. It returns null when the point is not enclosed.
  - Serialization is `version: 2`. Version 1 data (no `levels`, including plans already in localStorage) is migrated by `load()` onto a single default level; entities on an unknown level, and walls whose nodes are on different levels, are dropped.
  - Units are **centimetres**; plan coords are x right, **y down** (screen-like). The grid snap is 10 cm (`GRID` in `geometry.js`).
  - Every mutating method calls `emit()`; wrap multi-step edits in `model.batch(fn)` so listeners fire once.
  - `computeWallPolygons(model)` produces mitred wall outlines at shared nodes; both the 2D editor and the 3D view render walls from it.
  - `History` is snapshot-based (serialized JSON strings). The UI calls `history.commit()` after each *completed* user action (via the editor's `onCommit`), not on every model change — so drags don't flood the undo stack.
- **`js/catalog.js`** defines the stair kinds (`STAIR_KINDS`, `stairKindSpec`, with `TREAD` and `SPIRAL_POST`), the furniture library (`FURNITURE_TYPES`, `furnitureSpec`, `furnitureParts`), the wall styles (`WALL_STYLES`, read through `wallSpec(style)`, whose `look` — `solid`/`glass`/`railing` — is what renderers branch on, plus `BARRIER_HEIGHT` and the `RAILING` bar sizes) and the opening types with default width/height/sill, plus wall, floor (`FLOOR_DEFAULTS`) and stair (`STAIR_DEFAULTS`) defaults. Doors (`door`, `door_double`, `door_slide`, `door_garage`) carry `style` (`swing`/`slide`/`garage`) and `leaves`; windows (`window`, `window_tall`, `window_full`, `window_small`, `window_double`, `window_double_tall`, `window_double_full`) carry `panes`. **Renderers branch on those fields, never on the type key** — use `openingSpec(type)`, which fills in the defaults. `height: null` means full wall height; `align: 'top'` hangs the opening `head` cm below the ceiling (the small window). Adding a type means adding it here, a `TOOLS` entry in `editor2d.js` and a palette button in `index.html`.
- **`js/editor2d.js`** (`Editor2D`) handles tools (select/wall/curve/split/floor/fill/cutout/stairs/openings), hit-testing, dragging and the context menu. Everything drawn on a wall goes through `wallPoint`/`wallScreen`/`samplesAlong`/`strokeAlong`/`wallQuad` (which follow the arc) and `traceWall`/`traceWallSide` (which draw wall bodies with `ctx.arc`), so opening symbols bend with the wall for free. A selected wall shows a round handle at the middle of its centre line: dragging it sets `bulge`. Every wall-drawing tool (wall, curve, the three barriers) carries a `wallStyle` in its `TOOLS` entry — `isWallTool()` is the test, and `wallClick` just forwards it to `addWall`; `wallFill`/`wallStroke` pick the body and outline colours from the style. The curve tool keeps the clicked points in `chain.pts` and refits the whole chain's bulges from a spline through them on every click (`refitCurve`). A `TOOLS` entry carries `stairKind` or `furniture` to say what a click places — the furniture tools are generated from `FURNITURE_TYPES`, so the palette cannot drift from the catalog. `furnitureSpot()` is the wall snap (within 60 cm a piece turns to the wall and backs onto it; Alt places freely) and is used for both placing and dragging, and `rotateHandlePos()` + the `rotate` drag case turn stairs *and* furniture, snapping to 15°. It subscribes to `model.on()` and talks back to `main.js` only through callbacks (`onSelectionChange`, `onCommit`, `onToolChange`, `onStatus`). It only hit-tests and draws the active level; the level below is drawn ghosted underneath, and the active level's floors are opaque so they cover that ghost. `main.js` calls `onLevelChange()` when the active level changes.
- **`js/view3d.js`** (`View3D`) rebuilds the Three.js scene from the model on change (`scheduleRebuild`), one group per level at its elevation (`buildLevel`). A curved wall is stepped into short boxes along its arc (`buildCurvedWall`, `CURVE_STEP`), each in its own tangent frame, with openings left out of the solid exactly as in the straight builder; an opening's filler is a straight unit on the chord of its span. Wall styles dispatch in `buildLevel`: a railing is built from `buildRailing` (top bar plus posts), a glass barrier from the normal builders with the glass material and an `addCapRail` on top. `addStairs` dispatches on the stair kind (solid steps, floating treads, or treads winding about a post), and `addFurniture` emits one box per `furnitureParts` entry in the item's own frame, picking the material its `mat` names. `solidSpans`, `wallFrame` and `addBar` are the shared pieces, and they follow a curve as readily as a straight run. Levels above the active one use transparent material clones. `setActiveLevel()` animates the camera by the change in elevation. `main.js` imports it **lazily** via dynamic `import()` so the 2D editor keeps working if the CDN is unreachable.
- **`server/`** is the backend, and it is deliberately small:
  - **`server/server.js`** — `node:http`, no framework: routes, a static file server with an **allowlist** (`PUBLIC_FILES`/`PUBLIC_JS`, so the server's own sources are never downloadable), and the API. `/` and `/s/<token>` both serve `index.html`; `/invite/<token>` serves `invite.html`. Mutating `/api` calls must be JSON and same-origin, which with the `SameSite=Lax` cookie covers CSRF. `createApp({ dataDir })` is exported so the tests can run it on port 0.
  - **`server/db.js`** — the only file with SQL in it. `openDb(dir)` creates the schema and returns the queries, so moving off SQLite later means rewriting this one file. Tables: `users`, `invites`, `sessions`, `plans` (a plan carries its own `share_token`/`share_mode`).
  - **`server/auth.js`** — scrypt password hashing, the session cookie, and an in-memory rate limiter for login and invite attempts.
  - **`server/cli.js`** + **`add_user.sh`** — the operator's door: register an email, print its invite link. The invited person sets their password at `/invite/<token>`, and that is the only way an account is created.
  - **Sharing is not DRM:** a browser can only draw a plan it has been sent, so `view` and `copy` links deliver the same JSON. `view` hides the editing interface and the export button, `copy` adds "Edit copy". Say so plainly rather than implying the data is locked away.
- **`js/cloud.js`** holds everything that talks to the backend: the account bar, the sign-in / plans / share dialogs, explicit saving (the model's change event sets a dirty dot; `Save` and `Ctrl+S` PUT it) and preview mode. On `/s/<token>` it loads the shared plan, calls `editor.setReadOnly(true)`, sets `body[data-mode="preview"]` and shows the banner. **Preview never writes `localStorage`**, so looking at someone's share cannot overwrite your own plan; "Edit copy" writes it deliberately, after a confirmation, and reloads `/`.
- **`js/editor2d.js`** has a `readOnly` flag for that mode: the tool is forced to `select`, drags only pan, and the editing handles are neither hit-tested nor drawn.
- **`js/main.js`** wires everything together: the header toolbar and the left palette (one delegated `onChromeClick` bound to both; the palette is an accordion — `openPaletteGroup` keeps a single `<details>` open, and `onToolChange` opens the group that owns the tool a keyboard shortcut picked), level switcher (`syncLevel()` runs on every model change, so undo/import that changes the active level is picked up), keyboard shortcuts, properties panel, layout modes (2D / split / 3D), JSON import/export, and autosave of `model.serialize()` to `localStorage` (debounced, with try/catch because storage may be unavailable). If nothing is saved, it loads `createSampleModel()`.
